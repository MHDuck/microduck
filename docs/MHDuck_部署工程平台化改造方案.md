# MHDuck 部署工程平台接口改造方案

更新：2026-10-30。对应：[平台控制接口协议](MHDuck_平台接口协议_v1.1_设计稿.md)。
本版替代之前的平台管理型设计：算法侧只交付机器人控制、运行设置和状态，不建设账号权限、租约、版本发布或文件管理系统。
后续实现只在 dzh_voice 分支进行，不改 master/dzh、训练参数或现有模型衔接。

## 1. 分工

|算法 / 部署侧负责|平台 / 运维侧负责|
|---|---|
|行走、坐站、技能、头/身体/嘴部、声音的调用入口|页面、App、摇杆及按钮交互|
|语音、行走发声等运行开关|用户登录、账号权限、设备绑定、多用户分配|
|已有电量、温度、电流、策略、故障状态|公网网关、TLS/WSS、远程链路、访问控制|
|复用现有视频入口，提供地址和接入参考|视频页面嵌入或 WebRTC 客户端适配|
|参数检查、连续目标超时、单输入源互斥|状态展示、日志/CSV 导出、业务记录|
|只读程序版本和已部署动作清单|软件包上传、发布、升级、回滚及模型文件管理|

平台所说“是否开语音/行走声音”直接用 settings.set，不为每种开关组合做一份程序。
程序升级继续使用现有部署/updater 流程，首期不增加 versions.*、models.*、runtime.restart 等接口。

## 2. 最小实现结构

```text
平台 / App ── WebSocket :8000 ── 薄接口适配层 ── 现有 robotd
                                      │
开发键盘 ────────────── 共享命令/特性模块 ─┘
                                      │
                       原 speech 识别、行走发声逻辑

现有 mediad ── :8080 视频页面 + :8443 WebRTC 信令（复用）
```

- robotd 保持唯一电机输出、模型推理、技能时长和安全保护，不新写第二套控制器。
- 接口层优先用 Python 复用当前键盘/语音代码；作为独立 systemd 服务启动，不强制新增 Rust 网关 crate。
- 仅增加一组简单的 cmd → 现有 RPC 映射、设置对象和状态转换；状态自动推送，无订阅配置接口。
- 不实现 session.open、control.acquire/renew、角色权限、配置 revision/CAS、operation 数据库或硬件确认工单。
- 这是可信内网接口。对外部署由平台网关负责认证、加密和过滤；8000、8080、8443 均不可直接裸露公网。

## 3. 控制适配：复用现有代码

|对外接口|复用位置 / 最小修改|
|---|---|
|robot.info / state|现有 robot.health、robot.state、模型配置和 mediad 地址；统一少量展示字段|
|robot.enable|现有 robot.enable stand_up 路径 / robot.relax；正常使能不重启 robotd|
|robot.move / stop|现有 robot.move / robot.stop；外部 wz 映射内部 vyaw|
|robot.mode|提取键盘 drive/head/body 切换：停车、清旧头/身体目标、启停 body pose|
|robot.head / pose / mouth|现有 robot.head / robot.pose / robot.mouth；嘴部保持独立|
|robot.action|原 robot.do；补绝对 sit/stand/walk 包装，不把重复 sit 直接变成 sit_toggle|
|robot.sound|现有 robot.sound 与 duck-voice 情绪组合，不新做音频播放器|
|settings.get / set|一份运行设置对象，复用 SpeechInput / WalkingVoice 启停|
|robot.shutdown|现有 robot.shutdown|
|可选 drive_mode / logs / instrument / chorale|现有 setMode、日志、theremin、chorale；不支持时不公布|

绝对坐站优先在 robotd 补小型目标接口，由原 Sit 状态判断是否需要转换；接口层不自行猜测实际姿态。
drive/head/body 是输入模式，与 drive_mode=walk/roller、动作目标分开；使能完成默认 drive，站立就绪后直接 move，不要求先 action=walk。
action=walk 仅作为 stand 的兼容别名，不另建 Walk 任务生命周期或强制锁定某份模型；平台使用 stand / move 即可。
mode 切换不自动起立/使能，stop 不切 mode 或坐站；坐姿要行走先在 drive 下明确 stand，头/身体控制按当前模型和姿态能力校验。
从 head/body 返回 drive 后可直接 move，技能正常收尾后也不需要补发 walk；重复 enable=true 不重起身、不重置已有模式。
行走转坐下、起立结束、技能结束接哪份模型均保持当前 master 衔接，不把旧设计的额外 2 秒等待或新时长引入本轮。
不新增站稳/触球成功检测：只报告现有流程结束，实际姿态无可靠来源就 unknown。

action 事件使用原请求 id 关联，随现有动作生命周期发 running/finished/failed。
不建设持久化任务系统；关机、网络断开后无法确定的动作结果不自动重做。

## 4. 保留的最低限度保护

### 4.1 无续期接口，但连续运动仍需超时

平台按住摇杆时每 50 ms 发送当前速度，松手发送 stop。这是运动目标保持要求，空闲不需要业务心跳。
连接保活用 WebSocket 标准 Ping/Pong：服务端每 5 秒 Ping，5 秒内未收到对应 Pong 则终止连接；浏览器自动回应，App 库配置自动回应。
不新增 JSON 心跳接口。前端连续 2 秒没收到 state 就禁用控制并关闭旧连接；网关中转时两段链路分别保活，设备端失效须传递到 App。
不能仅靠 TCP/WS 的 close 回调发现 Wi-Fi 消失，也不能把标准 Pong 当成运动更新。
头/身体/嘴/声音保持/连续翻滚同样只在保持期间发送，停止更新后 500 ms 释放对应目标。
WS 确认关闭或保活失败时停止新行走、撤销该连接语音动作、释放保持目标；技能按现有控制器安全收尾。
正常退出：前端停发送定时器→stop reset_pose=true→等应答（最多 1 秒）→close(1000)。页面隐藏/切后台同样关闭控制连接；被系统杀掉则依赖超时兜底。
断连停车保持，不自动卸力；需要卸力先显式 enable=false。协议第 1 节已列明主动退出、异常、后台和重连规则。
异常可按 1/2/5/10 秒退避重连，主动退出/后台不自动重连；只读新状态，不重放速度/技能、不自动起身或恢复语音动作。
连接清理绑定该连接实例，旧连接延迟到达的关闭回调不能清掉后来接管的输入端。视频断开与控制断开分开处理。
500 ms 检查必须位于控制侧或可靠的现有超时路径：接口进程崩溃后也不能留下持续非零速度；
不能由接口层无限重发最后一次目标，让底层误以为平台仍在操作。

连续目标只保留最新值，慢连接限制队列，失效/关闭后的消息不执行。
离散动作使用连接内小型请求去重缓存即可，不将连续运动写入持久日志或缓存所有 20 Hz 请求。
参数检查、模型可用性、过流/倒地保护仍保留；本次不改保护阈值。

### 4.2 一个输入来源开关，不建设用户权限系统

同一时刻仅一个写入端：首个控制连接自动关联输入来源，断开自动释放，不给前端发 lease ID。
其他平台连接可读，普通运动写返回 BUSY；平台网关负责把多用户合并成一个设备控制连接。
本地键盘开始调试时显式进入本地输入模式、清除平台目标；平台变只读。
切换等待当前技能安全收尾；退出键盘不恢复平台旧目标，平台需重新明确使能/控制。

这个简单互斥需要覆盖 keyboard、padd 和旧 WebRTC 控制写入口，不能仅在新 WS 层放一个 Python 变量。
首期可把未使用的旧网络运动写入口禁用，mediad 视频不受影响；不同时改造所有旧客户端成新权限体系。
普通 stop/卸力不因“不是当前输入端”而被阻塞；正常退出脚本只清理自己仍持有的输入目标，避免卸掉后来接管的机器人。
输入来源是本地连接管理，不是远端可自报的用户角色；不暴露远程抢占/任意执行命令。

## 5. 功能设置与键盘兼容

settings.set 只修改本次传入字段，先整体验证，未知字段/越界拒绝。暂不新增落盘、临时/永久两套配置或版本号。
语音 off/preview/on、行走声音开关默认均关闭；接口服务自启不使能机器人、不启动麦克风。

|设置变化|实现|
|---|---|
|语音 off|结束识别进程，释放麦克风，撤销其运动输入|
|语音 preview|原识别逻辑，只输出识别事件|
|语音 on|复用现有人工优先、零速等待、最长 3 秒行走等门控；不增加 voice.arm，不自动使能|
|识别增益/阈值|更新/必要时仅重启识别进程，清空旧识别队列，不重启 robotd|
|行走发声及情绪/间隔|复用 WalkingVoice，热更新，不改变身体运动|
|sound_only|保持零 mouth RPC，不因“只发声”额外发送闭嘴命令|

运行中一台机器只保留一份识别/行走发声实例。提取共享模块供键盘和接口服务调用；
键盘独立调试时仍可使用原 CLI，不能要求开发者先打开平台，也不能同时抢占麦克风。
接口返回参数已接收后，启动中的识别通过 speech_status=starting/ready/failed 展示；失败必须有明确错误，不假装识别已可用。
平台端断连或键盘接管后，该平台输入的 on 降为 preview，重新设置 on 才恢复动作输入。

键盘原有按键、默认语音 off、Enter 研发重启习惯、C/L 日志与 CSV 保留。
平台的正常 enable 仅调用已有起身，不照搬每次重启 robotd 的调试操作。
空格效果对应 stop reset_pose=true；R/F 对应 sound + mouth；T 在键盘里仍可按状态选择坐/起，平台发明确目标。

## 6. 视频直接复用

当前源码确认：

- mediad/src/main.rs 默认视频页面端口 8080、信令端口 8443。
- mediad/webclient/index.html 使用 ws://<host>:8443 信令，建立 WebRTC 视频连接。
- scripts/camera-detect-test.py 返回 http://<host>:8080/ 页面入口。

先交付现有视频页面地址，平台 WebView/网页接入复用现有客户端；原生播放器适配由平台开发，不新增算法视频服务。
现有页面带机器人控制按钮，平台正式集成只使用视频部分，旧控制流禁用或受同一输入互斥限制。
已有视频尚未在本轮连接板子复测；不声称存在可直接播放的 RTSP/MP4 地址。
HTTPS 平台由其网关处理媒体页/信令的 HTTPS/WSS，不能靠忽略浏览器混合内容/证书错误解决。
摄像头按需采集、检测频率和图像处理参数保持，不为每个观看端新增推理任务。

## 8. 实施顺序与验收

1. 先交付 info/state 和已有视频地址，平台完成页面与状态展示。
2. 再接 enable/move/stop/mode/head/pose/mouth/action，逐个对照原键盘，先验证输入互斥和断流停车。
3. 接 settings 与声音：off 不访问麦克风、preview 零运动、on 只支持既定五口令且不自动使能。
4. 最后接关机和可选接口；平台负责多用户、网络保护、视频 UI 与 CSV 导出。

必须验证：停止速度帧但连接不断也能 500 ms 停车；接口进程崩溃不持续运动；重复坐下不变起立；
重复动作请求不重复踢腿；断网/重连不恢复旧动作；键盘和平台不抢写；声音/日志/视频卡顿不阻塞运动。
状态只能使用已有测量/估算数据，不把策略标签当姿态成功；无数据明确显示未知。
先记录既有测试失败基线，再做针对性回归；本轮只修订两份设计文档，未实现、部署或实机测试接口。
